3. Course project 30 points

🎯 What the project is graded on: experiment design, how you evaluate what you built, your analysis, and your ideas and creativity — not on how good the numbers turn out. A solution that scores poorly but is compared well and explained is worth more than a pretty number nobody can trace.

The task

Pick one real image or video set, propose two or three solutions that take different routes, actually run every one of them, measure on both axes, and pick the best trade-off:

real images / video → preprocessing → solution A / B / C (feature–geometry · CNN · detection …) → accuracy + speed / resources → pick the best trade-off

Must have:

  • Your data, described and explored — what it looks like, its columns, files and metadata, and an EDA
  • An experimental setting — how the data is split (train / validation / test) and what else every solution shares
  • Three or more core techniques your solutions are built on — from the course or from the literature, but every one explained in full, in your own words: the theory · what it does for this project · an example figure (e.g. “median filter because the noise is salt-and-pepper”, not “because the sample code had it”)
  • Each core technique can be taken by one group only — hand in your list with your topic (week 8); first come, first served, and the instructor posts the list of taken ones. A technique another group has taken may still appear in your solutions, but it does not count as one of your core techniques
  • Two or three solutions — each with its own workflow / pipeline / framework, plus pros and cons · they must differ in the pipeline, the data preparation or the method — swapping only the algorithm or model inside one step of the same pipeline does not count as a new solution (e.g. YOLOv8n vs YOLOv8s vs RT-DETR in the same detect-and-count pipeline, or an SVM vs a random forest on the same features). Solutions that count: A frame difference + blobs (nothing learned) · B detect every frame + track · C crop to the crossing, then count with an open-vocabulary model
  • Measured on two axes — accuracy (a metric that fits the task, the same one for every solution on the same data) and speed / resources (time, memory or parameter count, as numbers)
  • Results need not be good — the points are for the idea, the comparison, and the analysis of why things came out the way they did
  • Working as a group (2–3 people)? Say who did which part — a “who did what” slide in both the proposal and the demo deck: each member’s student ID and real full name, and what that person was responsible for (the EDA, which core technique, which solution, which part of the notebook, the slides / the talk) · and each solution’s notebook section starts with its author’s name · not needed if you work alone (example below)

Slides 20+ pages · page numbers on every slide · 15+ minutes including a live run of the notebook (no code needed on the slides) · hand in clip + slide PDF + .ipynb
#Criterion
C1Proposal recap — your proposal in brief, all six points (one score for the whole item):
  1. Problem — input, output, problem, challenge
  2. Dataset — where it comes from, what is in it, how it is split
  3. Core techniques you use
  4. Solutions — the two or three you built, and the workflow of each
  5. Evaluation metric — which one, and why you chose it
  6. What changed after the proposal comments, and why — or why nothing did
C2Experimental setting — the data split and experiment settings you actually used, and why
C3Parameter setting — the parameter values each solution actually used, and why you chose them
C4Analysis per solution — the metric value every solution got, all on the same data · what each one got and why
C5Speed / resources — time, memory or parameter count for every solution — as numbers

C11Clean notebook — a section per solution with headings (groups: each heading names its author) · meaningful variable / function names · no duplicated code

Running code is not a score — if it doesn't run you can't submit (does not run = 0 on C10). The points are for explaining what every cell does and reading your own results.

5. Sample Q&A (prepare for these)

Proposal session
  • Why these core techniques — and where did each one come from (which session, which paper)?
  • What really separates solution A from B? If they tie, which do you pick?
  • What about this dataset needs care before you use it?
Demo session
  • What does this cell do? If you delete it, what changes?
  • Why this kernel size / threshold / pretrained model?
  • Which cell produced the number on this slide?
  • Double this parameter — which way does the result move, and why?
  • Why wasn't the more accurate solution the one you chose (or the other way round)?

6. AI and attribution

You may use AI to help write code, but you must understand every cell you submit — the demo (C10) and the Q&A (C16) are where that is checked. If you use a pretrained model or borrow code or data, cite the source on the slides and in the README (no citation = treated as copying).
